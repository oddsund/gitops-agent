0How this course works

~30 min setup, nothing merged

This curriculum was carved out of real work: a stack of five pull requests (#7–#11) that moved gitops-agent's install and update machinery out of bash and into the binary. Those PRs are now closed, and their branches live on as reference/* — the answer key. Your job is to produce the same functionality yourself, chapter by chapter, and only then compare.

The contract

  • You type the code. All of it. The point of this course is the hours your fingers spend in Go, not the diff at the end.
  • Claude is your tutor, not your ghostwriter. Two skills live alongside this document: tutor (Socratic help — escalating hints, never code) and grade (invoke when you believe a chapter is done; it runs the quality gates, reviews your diff on its merits, then compares against the reference).
  • Don't peek at reference/* until grade shows it to you, or you explicitly surrender a chapter. The bash scripts already on main are your spec for Part 1 — that's not peeking, that's reading requirements.
  • Every assignment ends green. gofmt -l ., go vet ./..., go test ./... — clean, before every commit. CI enforces all three, so CI is your grader of first resort.

The loop, per chapter

  1. Read the chapter. Follow the reading links you don't already know cold.
  2. Branch from main: git checkout -b feat/ch03-latest-release main (use the branch name the chapter gives you).
  3. Build the assignment. Ask the tutor when stuck — it will make you earn it.
  4. Run the gates locally. Commit with a conventional-commit message (feat:, test: …) that explains why in the body.
  5. Push, open a PR to main, let CI run.
  6. Invoke grade. Fix what it finds. Merge when it passes and you're satisfied.

One-time setup

This curriculum and the two skills live on the branch claude/go-gitops-agent-curriculum-6v7ymk, which deliberately never merges to main — so your assignment branches won't contain them. Overlay them as untracked files once, and they'll follow you across every branch without ever landing in a PR:

# from your clone, on any branch:
git checkout claude/go-gitops-agent-curriculum-6v7ymk -- .claude docs/curriculum
git restore --staged .claude docs/curriculum

# keep them out of git status and out of your PRs:
printf '.claude/\ndocs/curriculum/\n' >> .git/info/exclude

.git/info/exclude is a local-only ignore file — like .gitignore, but never committed. If a chapter's files ever look stale, re-run the first command to refresh them from the branch.

Then verify the toolchain:

go version          # anything ≥ the version in go.mod is fine
go test ./...       # should pass on a fresh clone
gofmt -l .          # should print nothing
go vet ./...        # should print nothing
shellcheck --version  # needed for chapter 10
Tracking progress

The checkboxes at the end of each chapter are stored in your browser only. If you use beads (bd) in this repo, the tutor can also file an issue per chapter and close it when graded — say so and it will.

Part 0 · Orientation

1The machine you're changing

~1 h read & explore, no PR

gitops-agent is one Go module with one job: a daemon that keeps docker compose services on a host matching what a git repository says they should be. The repo it syncs is the desired state and the trust boundary — anyone who can push to it can run containers on the host. Every design decision you'll meet in this course bends around that fact.

The layout is the standard shape for a small Go service, and it's worth internalizing because Part 1 and 2 add packages to it:

cmd/gitops-agent/   package main — flag parsing, signal handling, the reconcile loop
internal/
  config/           config.toml + services.toml parsing (TOML → structs)
  gitsync/          fetch + hard reset; tree-hash change detection
  sopsdecrypt/      decrypt secrets.enc.env → tmpfs, never the checkout
  deploy/           docker compose up / down
  schedule/         adaptive polling cadence (idle 300 s ↔ active 15 s)
  state/            persisted map of what's deployed, as JSON
  statusserver/     HTTP status page + snapshot file
docs/               operator docs — how-it-works.md is the loop in prose
systemd/            the units a host runs; update.bash (your Part 1 spec)
scripts/lib/        github-release.bash (spec for the verify logic)

internal/ is not a convention, it's a compiler-enforced rule: packages under it can only be imported from within this module. That's why the agent can keep these packages' APIs blunt and change them freely — nobody outside can depend on them.

Read

  • docs/how-it-works.md — the loop above, in prose, with the reasoning (hard reset over pull, last-known-good manifest, full reconcile for drift).
  • cmd/gitops-agent/main.go — read run() and runOnce() top to bottom with how-it-works.md beside it. This is the best 300 lines of orientation in the repo.
  • go.dev — Organizing a Go module — why cmd/ and internal/ look like this.
  • A Tour of Go — skim as a refresher if it's been a while; you want structs, methods, slices/maps, and error basics warm before chapter 3. Deeper: Effective Go.
Assignment 1 — field questions

No code, no PR. Explore until you can answer these from the source (not the docs). Write your answers down — one sentence each — and check them with the tutor if you're unsure:

  1. A commit lands that only touches services/blog/. Which services get docker compose up on the next cycle, and which function decided that?
  2. You push a services.toml with a syntax error. What happens to the currently running services, and which log line proves it?
  3. Why does teardown run before deploy in the same cycle? What breaks if you swap them?
  4. Where do decrypted secrets land on disk, and why there of all places?
  5. runOnce returns (bool, error). Who consumes the bool, and what behavior does it drive?
  6. What happens to the loop when you systemctl restart the agent mid-deploy — and which lines in main() make that true?

Done when

  • You can sketch the cycle figure above from memory.
  • All six answers are written down and survive a tutor spot-check.
Part 0 · Orientation

2Guided read: the dispatch seam

~45 min scratch branch, no PR

Everything you build in Parts 1 and 2 hangs off one commit that is already on main: 63f31e8, which taught cmd/gitops-agent to dispatch subcommands. It's 140 lines including tests, and it's your model for what a finished assignment in this course looks like — small, motivated by a constraint, and tested at the seam.

git show 63f31e8   # read the commit message first, then the diff

The constraint that shaped it: gitops-agent.service and existing tooling invoke the binary bare, or with flags (-version, -config). That invocation shape is load-bearing and must keep meaning "run the daemon". So dispatch triggers only when os.Args[1] exists and doesn't start with -:

What to notice while reading

  • The registry is a map of functions. map[string]func(args []string) error — functions are values in Go; storing them in a map is the whole "framework". Each subcommand file registers itself in init(), so adding a subcommand never edits main.go again.
  • dispatch takes stderr io.Writer, not os.Stderr. That one parameter is why dispatch_test.go can assert on error output with a bytes.Buffer. Injecting the seam you want to observe is the testing move this whole course keeps making.
  • The tests are table-driven. TestIsSubcommand is the canonical Go pattern: a slice of cases, one t.Run per case. You'll write a lot of these.
  • Errors cross the boundary as values. Subcommands return error; only dispatch decides what that means for the process (message + exit code). Policy at the edge, plumbing in the middle.

Read

  • Go by Example — command-line subcommands — the standard-library way; compare it with what this repo chose and ask why.
  • Go wiki — table-driven tests — the test shape you just read, explained.
  • pkg.go.dev — io.Writer — the single most load-bearing interface in Go; one method, endless test seams.
  • Effective Go — init — what init() is and when it runs. Registration is its one broadly accepted use; don't reach for it beyond that.
Assignment 2 — a throwaway subcommand

On a scratch branch (git checkout -b scratch/ch02-dispatch main — it will never become a PR), prove you understand the seam by using it:

  1. Add a cmd/gitops-agent/hello.go that registers a hello subcommand in init(). It errors if given arguments, otherwise prints hello from gitops-agent.
  2. Write hello_test.go: one test that it rejects arguments, one that dispatching hello through dispatch() returns exit code 0.
  3. Build and run all four invocation shapes: bare (ctrl-C it), -version, hello, bogus. Confirm each behaves as the figure predicts.
  4. Delete the branch. The knowledge is the artifact.

Done when

  • All four invocation shapes behaved as you predicted before you ran them.
  • You can explain why usage() lists subcommand names sorted (hint: iterate a Go map twice and watch the order).
Part 1 · gitops-agent update

3Ask GitHub for the latest release

1–2 h PR · feat/ch03-latest-release

The mission for Part 1: the daily self-update currently lives in systemd/update.bash plus scripts/lib/github-release.bash. Over the next four chapters you will port it into the binary as internal/selfupdate, wired up as gitops-agent update. Those two bash scripts are your functional spec — read them the way you'd read a requirements doc. Same steps, same verification, same leave-the-installed-binary-alone-on-any-failure guarantee.

This chapter builds the first slice: a new package that can answer one question — what is the latest released version? — against the GitHub API, with a test suite that never touches the network.

Concepts

  • A config struct instead of a parameter list. Start a Config struct now (Repo, Token, and the two test seams below) and grow it through Part 1. In Go, a struct of plain fields with documented zero-value behavior ("empty means the real GitHub") is the idiomatic alternative to both global state and six-argument functions.
  • Decode only what you need. The releases API returns a huge JSON object; you need one field. Define a struct with just TagName string and a json:"tag_name" struct tag — encoding/json ignores the rest. This is normal and good.
  • The request/response ritual. http.NewRequest → set headers (Accept: application/vnd.github+json; Authorization: Bearer … only when a token is set) → client.Do(req) → defer resp.Body.Close() → check resp.StatusCode → decode. Every step someone skips becomes a production bug; the body-close and status-check are the two everyone skips first.
  • Wrap errors on the way up. fmt.Errorf("querying latest release: %w", err) — the %w verb keeps the cause inspectable with errors.Is/errors.As while the prefix tells a log reader which HTTP call died.

Read

  • systemd/update.bash (on main) — the "resolve the latest tag" block is this chapter's spec, including the empty-tag failure case.
  • Go blog — JSON and Go — how encoding/json maps JSON to structs; why partial structs work.
  • Go blog — Working with Errors in Go 1.13 — the %w/errors.Is model you'll use in every package from now on.
  • pkg.go.dev — httptest.NewServer — a real HTTP server on a random local port, per test. Also skim http.ServeMux for routing your fake.
  • Go by Example — HTTP client — the minimal ritual, if you want it in one screen first.
Assignment 3 — internal/selfupdate, first slice

Branch feat/ch03-latest-release from main. Create internal/selfupdate/selfupdate.go and its test file. Build:

  1. A Config struct: Repo ("owner/repo"), Token, plus test seams APIBaseURL and HTTPClient *http.Client — each falling back to the real default when zero. Document the zero-value meaning on each field.
  2. latestReleaseTag(cfg Config) (string, error) hitting GET {api}/repos/{repo}/releases/latest, decoding only tag_name.
  3. A package doc comment saying what the package will become (a port of update.bash — say so; future-you reads this).

Acceptance criteria

  • Happy path returns the tag; a test proves it against an httptest.Server serving a GitHub-shaped JSON body.
  • Non-200 responses and an empty/missing tag_name both return errors that name the URL or repo — tested.
  • When Token is set, the request carries Authorization: Bearer <token>; when unset, no auth header. Test it by asserting on r.Header inside your fake handler.
  • Every response body gets closed; no test opens a real network connection.
  • Gates green: gofmt -l . silent, go vet ./..., go test ./....

Done when

  • PR open against main, CI green, grade passed.
Nudge (open only if stuck)

Write the fake server first. A http.HandlerFunc that does fmt.Fprintf(w, `{"tag_name": %q}`, "v1.2.0") is a complete GitHub for this chapter's purposes — and once it exists, the shape of the code under test falls out of what the test needs to inject.

Part 1 · gitops-agent update

4Download and verify

1–2 h PR · feat/ch04-fetch-verified

Now the security-critical middle: download a release asset to a temporary file and verify its SHA-256 checksum against the .sha256 file published beside it. The contract, straight from github_release_fetch_verified in the bash spec: on any failure, the temp file is removed and an error is returned. A caller must never be able to install an unverified binary just because it forgot to check something.

Concepts

  • Stream, don't slurp. The binary goes resp.Body → io.Copy → file, never through a []byte in memory — this runs on small boxes. The checksum file, a few dozen bytes, can be slurped with io.ReadAll. Choosing per payload is the skill.
  • os.CreateTemp and the cleanup discipline. Every early return between "temp file created" and "verified" must remove it. A named cleanup := func() { os.Remove(path) } called at each failure exit is one honest way; think about why a plain defer is wrong here (the success path must keep the file — though chapter 5 shows the defer-that-becomes-a-no-op trick).
  • Hash a file without reading it twice. sha256.New() is an io.Writer — io.Copy(hasher, file) then hex.EncodeToString(h.Sum(nil)). The standard library composes around io.Reader/io.Writer; when two stdlib types won't connect, you're probably holding one wrong.
  • Parse defensively. The published .sha256 file is <hash>␠␠<filename>, and the filename never matches your temp path — so extract the hash column (strings.Fields) and compare, rather than shelling out to sha256sum -c. The bash spec has a comment making exactly this argument; port the comment's reasoning, not just the code.

Read

  • scripts/lib/github-release.bash (on main) — this chapter's spec: github_release_fetch_verified, including the token path and the checksum-parsing comment.
  • pkg.go.dev — io.Copy and os.CreateTemp — the two workhorses; read CreateTemp's pattern argument docs, you'll want a recognizable prefix.
  • pkg.go.dev — crypto/sha256 — note New() returning a hash.Hash, which is an io.Writer.
  • Go blog — Defer, Panic, and Recover — defer's evaluation rules; you need them to reason about the cleanup question above.
Assignment 4 — fetchVerified

Branch feat/ch04-fetch-verified from main (merge chapter 3's PR first). Extend internal/selfupdate:

  1. Grow Config with AssetName and DownloadBaseURL (test seam, defaulting to https://github.com).
  2. fetchVerified(cfg Config, tag, destDir string) (string, error): download {download}/{repo}/releases/download/{tag}/{asset} into a temp file in destDir, fetch the sibling .sha256, extract the expected hash, hash the temp file, compare. Return the temp path only on success.
  3. Helpers as you see fit — a shared "GET with headers, non-200 is an error" helper will earn its keep; so will separate download-to-file and download-to-memory functions.

Acceptance criteria

  • Happy path: returns a path whose contents equal what the fake server served — tested with your chapter 3 fake grown to serve download URLs.
  • Checksum mismatch: error mentioning both hashes, and the test walks destDir to prove no temp file survived.
  • Missing asset or missing .sha256: errors that say what's missing and that nothing was installed; the missing-checksum error should refuse loudly ("refusing to install an unverified binary" is the spec's wording — keep that spirit).
  • Unparseable checksum file: error, no leftover file.
  • Errors are wrapped with context at every level; gates green.

Stretch (optional)

  • The token path: against a private repo the plain download URL 404s, so the bash spec resolves numeric asset IDs via the API and downloads those with Accept: application/octet-stream. Port it if you're feeling it — the reference has it, and grade will treat it as a difference, not a defect, if you skip it.
Nudge (open only if stuck)

Test-order trick: write TestFetchVerified_ChecksumMismatch before the happy path. The failure test forces the cleanup structure into existence early; retrofitting cleanup after the happy path works is how leftover-file bugs get written.

5Install atomically, restart, attest

1–2 h PR · feat/ch05-update-orchestration

This chapter completes the package: the top-level Update(cfg) that decides whether an update is needed, and the three effects it orchestrates — install the verified file over the running binary, restart the service, and (between verify and install) check build provenance with gh attestation verify. It's also where the tests get interesting, because the effects are external commands.

Concepts

  • Atomic replacement. os.Rename within one filesystem is atomic: any process opening the path sees the old file or the new file, never a torn half-write. That's why chapter 4 put the temp file in filepath.Dir(cfg.BinPath) rather than /tmp — a rename across filesystems isn't a rename at all. The running binary keeps executing its already-open old inode until the restart. This one idea is most of what "safe self-update" means.
  • Running external commands. exec.Command("systemctl", "restart", name).CombinedOutput() — capture output so the error you wrap contains what systemctl actually said. For gh: exec.LookPath first, because a missing gh is policy ("skip, log, continue — the checksum already ran"), not an error. Note the asymmetry you must preserve: missing gh skips; failing gh aborts.
  • Faking commands in tests. The trick from the reference is worth inventing yourself: write a tiny shell script named systemctl (or gh) into t.TempDir(), make it record its argv to a file and exit 0 or 1, then t.Setenv("PATH", dir) — replacing PATH entirely, so the host's real binaries can't leak in. Now "did we restart the right service?" is a file read.
  • The defer-becomes-no-op pattern. Update can defer os.Remove(tempFile) right after a successful fetch: if install renames the file away, the remove fails silently; if anything aborts first, it cleans up. Compare with chapter 4's explicit cleanup and form an opinion.
  • Asserting on log output. The "gh not found, skipping" branch's only observable effect is a log line. log.SetOutput(&buf) + restore in t.Cleanup makes it testable. Ugly-but-honest beats untested.

Read

  • systemd/update.bash + scripts/lib/github-release.bash — the remaining spec: version-file comparison, install step, restart, attestation policy (and the GITOPS_AGENT_SKIP_ATTESTATION escape hatch).
  • pkg.go.dev — os/exec — Command, CombinedOutput, LookPath; note ExitError if you want richer failure info.
  • pkg.go.dev — T.Setenv, T.TempDir, T.Cleanup — the modern test-hygiene trio; all three self-undo after the test.
  • pkg.go.dev — runtime.GOARCH — for deriving the default asset name; the bash spec's uname -m case maps to a much shorter Go switch.
Assignment 5 — Update, end to end

Branch feat/ch05-update-orchestration. Finish internal/selfupdate:

  1. Grow Config: BinPath, VersionFilePath, ServiceName, SkipAttestation.
  2. Update(cfg Config) error: derive the asset name from runtime.GOARCH when unset (arm64/amd64 only — error otherwise), get the latest tag, read the installed tag from the version file (absent file = never installed), stop early with a log line when they match, otherwise fetch-verified → attest → install → write version file → restart.
  3. verifyAttestation in its own file: missing gh → log and skip; present-but-failing gh → abort with gh's combined output in the error; SkipAttestation → never invoke gh at all.
  4. Install: chmod 0755, rename into place, write tag + "\n" to the version file.

Acceptance criteria — each is one test

  • Already up to date: no download happens. Prove it with a fake server that fails the test on any request beyond releases/latest.
  • Installs a newer release: binary content replaced, executable bit set, version file updated, and the systemctl stub's recorded argv is exactly restart gitops-agent.
  • Checksum mismatch aborts: original binary byte-identical, version file unwritten, no temp litter.
  • Missing gh skips attestation: update succeeds, log output mentions the skip.
  • Failing gh aborts: original binary untouched.
  • SkipAttestation bypasses a failing gh: proves the flag short-circuits before invocation.
  • Gates green; no test touches the real network, real systemctl, or real gh.
Nudge (open only if stuck)

6Wire the subcommand

~1 h PR · feat/ch06-update-wiring

The package works; now give it a front door. gitops-agent update is a thin adapter: resolve environment into a Config, call selfupdate.Update, let dispatch handle the exit code. The interesting decisions here are interface decisions, not algorithms.

Concepts

  • Env vars, not flags — because compatibility. update.bash is configured by GITOPS_AGENT_REPO, GITOPS_AGENT_BIN, etc., and gitops-agent-update.service already sets them. Keeping the exact same names means a host migrates by changing one ExecStart= line. Interface compatibility is a feature you build, not an accident.
  • Secrets come from files, not the environment. The token is read from GITHUB_TOKEN_FILE (default /etc/gitops-agent/github-token), and a missing file is simply "no token". Environments leak — into /proc, logs, child processes; root-owned files don't.
  • A tiny helper is fine. envOr(key, def string) string — three lines, used six times, tested once. Resist both temptations: inlining it six times, and pulling in a config library for it.
  • Strictness at the edge. update takes no arguments — so error on any. Silent acceptance of gitops-agent update --force teaches users a flag that doesn't exist.

Read

  • systemd/gitops-agent-update.service (on main) — the unit that will run this; read its comments about why it runs as root and what ExecStart points at today.
  • The Twelve-Factor App — Config — the case for env-var config, so you can also see where this repo deliberately deviates (the token).
  • pkg.go.dev — os.ReadFile — note the read-then-check-error-later idiom for optional files.

Part 2 · gitops-agent install

7Embed the assets

1–2 h PR · feat/ch07-embed-assets

The mission for Part 2: provisioning a host — writing config.toml, installing the three systemd units, enabling the services — currently lives in external tooling. You'll move it into the binary as gitops-agent install, which means the binary must carry its own templates. That's this chapter: go:embed, plus the little line-substitution engine that turns the templates into host-specific files.

Concepts

  • go:embed compiles files into the binary. A //go:embed config.example.toml directive above a var ConfigExampleTOML string makes the file's contents a compile-time constant, verified by the compiler (a typo'd path is a build error, not a runtime surprise). One binary, no "where do the templates live on this host" problem — which is the whole point for a single-file agent.
  • Embed paths cannot climb. A pattern like ../config.example.toml is rejected — embeds only reach files in the embedding package's directory and below. The files to embed live at the repo root (config.example.toml, systemd/), so the embedding Go file must live there too: a small root package (package gitopsagent) whose only job is holding assets, imported by internal/installer. When a language rule forces a structural concession, write the reason down in the package doc — you'll do exactly that.
  • Template ≠ text/template. The substitution needed is "rewrite the line starting with User=", mirroring what a sed s/^User=.*/…/ did before. A scanner over lines with a prefix match does this in ~20 lines with zero new concepts for the file's readers — and critically, every untouched line (comments included) passes through byte-for-byte. Reach for text/template when you control the template; here the templates are real files a host also uses directly, and they must stay valid as-is.
  • Characterization tests. The guarantee "only the User= and ReadWritePaths= lines may differ from the template" can be tested literally: render against the real embedded template, then compare line-by-line against the template itself, asserting every other line is identical. This pins today's behavior down so refactors can't silently drift — the same technique you'd use to port any legacy system.

Read

  • pkg.go.dev — embed — short and complete; note the pattern rules that force the root-package move.
  • config.example.toml, systemd/gitops-agent.service (on main) — the four files you'll embed; find the exact lines (User=, ReadWritePaths=, repo_url, ssh_key_path, clone_path) that need substitution.
  • pkg.go.dev — bufio.Scanner and strings.Builder — the line loop; check Scanner's default buffer limit and decide whether these files could ever exceed it.
  • Characterization tests — the idea in one page; you're about to write one.
Assignment 7 — assets + the substitution engine

  2. internal/installer: a line-substitution helper (given prefix→value pairs, rewrite matching lines, first match wins, everything else byte-for-byte), plus renderServiceUnit(tmpl, user, readWritePaths) and renderConfigTOML(tmpl, repoURL, sshKeyPath, clonePath) — the TOML values quoted with %q.

Part 2 · gitops-agent install

8The idempotent installer

1.5–2 h PR · feat/ch08-installer

Now the orchestration: installer.Install(cfg), which must be safe to run on a fresh host, on an already-provisioned host, and on a host whose operator hand-edited the config — the same call, three very different correct behaviors. Idempotency isn't a property you add at the end; it's the design.

The three rules that make it idempotent

  1. config.toml is written once, then owned by the operator. If it exists, leave it — a hand edit sticks forever. (os.Stat, treat only os.IsNotExist as "go ahead"; any other stat error is a real error.)
  2. The rendered service unit's ReadWritePaths= comes from the config on disk, not from this call's inputs. Rule 1 means the disk config may disagree with the flags; the disk wins. So: write-if-absent, then read back through internal/config — reusing the daemon's own loader, so there's exactly one definition of what valid config means.
  3. Restart only when it matters. Write the unit, but remember whether its content actually changed (read-old, compare, write). Restart the service if the unit changed or it isn't currently active; otherwise say so and leave it alone. A provisioning tool that bounces a healthy service on every run trains operators to fear running it.

Concepts

  • Effects behind a helper. A systemctl(args ...string) error wrapper (variadic, wraps CombinedOutput output into the error) keeps every call site one honest line and gives your tests a single choke point to stub — the chapter 5 PATH trick again, this time with an appending log so one test observes a sequence of calls.
  • Security posture is code placement. Installing units is root-level behavior in a binary that otherwise never runs as root; it must be reachable only from the explicit subcommand, never from the reconcile loop. Say so in the package doc — in this repo, trust-boundary reasoning belongs next to the code that holds the boundary.
  • The update units ride along. Write gitops-agent-update.service and .timer verbatim from the embeds and enable --now the timer. And this is the moment to edit the source unit: point its ExecStart= at gitops-agent update (your chapter 6 work), replacing the old root-owned-copy-of-a-script arrangement — rewrite the unit's comment to explain why the old risk (root execing a user-writable script) doesn't apply to a root-owned binary.

Read

  • internal/config/config.go — the loader you're about to reuse; check what it validates so you know what "read back" can fail on.
  • pkg.go.dev — os.Stat / IsNotExist — the exists-check idiom and its third case people forget (an error that is neither nil nor not-exist).
  • systemd.exec — ReadWritePaths= — what the substituted line actually grants; you're generating security config, know what it means.

Part 2 · gitops-agent install

9Flags, users, and wiring

~1 h PR · feat/ch09-install-wiring

The front door for Part 2 — and unlike update, this one takes flags, because a human runs it interactively at provisioning time (env vars are for units; flags are for people; keep an opinion on which is which). The other new topic: figuring out who the agent should run as, when the command itself runs under sudo.

Concepts

  • flag.NewFlagSet, not the global flag. The daemon already owns the global flag set; a subcommand gets its own, created with flag.ContinueOnError so a parse failure comes back as an error for dispatch to render, instead of os.Exiting from the middle of a library call.
  • Required flags are your job. The flag package has no "required" — check for the zero value after Parse and return an error naming the flag. Ugly? Slightly. Explicit? Completely.
  • The SUDO_USER chain. sudo gitops-agent install runs as root, but the service should run as the human who typed sudo. Resolution order: -user flag → $SUDO_USER → current user. Then os/user.Lookup gets that user's home dir for the SSH-key default. Each step is a documented decision, not a fallback accident.
  • Keep the adapter thin. Like chapter 6: resolve inputs, build installer.Config with the real /etc paths, call Install. If logic wants to creep into install.go, it probably belongs in the package where it can be tested without root.

Read

  • pkg.go.dev — flag — FlagSet, ContinueOnError, and how defaults print in usage.
  • pkg.go.dev — os/user — Current and Lookup; note both can fail and what that means here.
  • man sudo (the ENVIRONMENT section) — what SUDO_USER is and when it's set; the whole chain rests on it.

Part 3 · The boundary

10The bootstrap script and the shim

1–2 h PR · feat/ch10-bootstrap

One step can never live in the binary: getting the binary onto a fresh host in the first place. This chapter is bash, deliberately — knowing where the Go/bash boundary belongs is a Go skill. You'll write scripts/install.sh (download → verify → install → exec gitops-agent install), then reduce the now-redundant update.bash to a deprecation shim.

Concepts

  • This repo's shell rules are law. set -euo pipefail and a strict IFS; long-running commands must show progress (curl gets -S -L but not -s for the big download — silent looks hung over slow SSH); shellcheck clean, with any disable justified in a comment. See CLAUDE.md.
  • Pin the transport. curl --proto '=https' --tlsv1.2 — refuse plaintext and ancient TLS even if a URL or redirect tries. Cheap to type, embarrassing to omit from a script whose whole job is trust.
  • mktemp -d + trap … EXIT is bash's t.TempDir(): the workdir cleans up on every exit path, success or failure. And install -o root -g root -m 0755 beats cp: it writes a temp file in the destination directory and renames — the same atomicity you built in chapter 5, provided by coreutils.
  • Deprecate loudly, break nothing. The shim keeps old hosts working: honor GITOPS_AGENT_BIN, print one clear stderr notice saying what to do (re-run scripts/install.sh), then exec "$BIN" update. exec replaces the process — exit code and signals flow through untouched, which is exactly what systemd needs.

Read

  • CLAUDE.md (shell section) — the house rules you're being graded against.
  • shellcheck — run it locally; read each finding rather than pattern-matching fixes.
  • Google Shell Style Guide — a defensible default for everything CLAUDE.md doesn't specify.
  • Your own chapters 3–5 — the script's verify steps mirror the Go you already wrote; keep the log lines consistent between the two, operators see both.

11Write it down

~1 h PR · feat/ch11-docs

The system changed shape; the docs still describe the old one. The final assignment is prose — and it's in the curriculum on purpose, because operator docs are part of what you shipped, and because writing them is the best audit of your own understanding. If a section is hard to write, you usually built something hard to explain.

What good looks like here

  • docs/install.md tells the reader what to run, in order of likelihood: bootstrap script first (with the "read it before you run it" caveat — the trust chain figure from chapter 10, in words), then the by-hand release path, then reference tables for both subcommands (flags for install, env vars for update — your chapter 6 PR table is most of this), then a migration section for hosts provisioned under the old regime: what they currently have, that nothing forces them to move, the one command that moves them, and what's safe to delete afterwards.
  • docs/security.md owns the trade. Moving the updater into the binary it updates gave up a real property: a separately-installed updater could heal a compromised binary on the next cycle; a self-updating binary can be shipped one bad release that permanently wedges updates. Write that down plainly — what was lost, why it's accepted (weigh it against the docker-group reality and the retired bash attack surface), and what a reader with a stricter threat model should do instead. Security docs that only list strengths are marketing.

Read

  • The Grand Unified Theory of Documentation — install.md is a how-to guide with reference tables; keep the modes separate and both get better.
  • docs/security.md (on main) — match its existing register: plain sentences, threats named concretely, no hedging.
